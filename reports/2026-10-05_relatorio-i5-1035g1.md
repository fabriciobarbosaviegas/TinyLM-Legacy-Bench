# Relatório Experimental --- Inferência de LLM no Intel Core i5-1035G1

## 1. Identificação do experimento

**Plataforma:** Lenovo IdeaPad S145-15IIL (82DJ)\
**Processador:** Intel Core i5-1035G1\
**Núcleos físicos:** 4\
**Threads lógicos:** 8\
**Memória RAM:** 8 GB\
**GPU:** Intel Iris Plus Graphics G1 (Ice Lake), integrada\
**Sistema operacional:** Kubuntu 26.04.1 LTS (x86_64)\
**Kernel:** 7.0.0-38-generic\
**Ambiente gráfico:** KDE Plasma 6.6.6 / KWin X11\
**Motor de inferência:** `llama.cpp`\
**Build do `llama.cpp`:** `b11370-bed0a8566`\
**Modelo utilizado:** `qwen2.5-0.5b-instruct-q5_k_m.gguf`\
**Backend no benchmark:** CPU\
**Threads testados:** 1, 2, 4 e 8

> **Nota sobre o modelo:** embora o arquivo utilizado tenha `0.5b` no
> nome, o `llama-bench` identificou o modelo como **Qwen2 1B Q5_K -
> Medium**, com aproximadamente **630,17 milhões de parâmetros** e
> tamanho de **492,32 MiB**. Para este relatório, a identificação
> retornada pelo próprio `llama-bench` é considerada a referência
> experimental.

------------------------------------------------------------------------

## 2. Objetivo

O experimento teve como objetivo caracterizar o comportamento do Intel
Core i5-1035G1 durante inferência local de um modelo de linguagem
quantizado utilizando `llama.cpp`.

Foram avaliados:

1.  desempenho de inferência com diferentes quantidades de threads;
2.  desempenho de processamento de prompt e geração de tokens;
3.  comportamento interativo do modelo;
4.  temperatura do processador durante o benchmark;
5.  frequência de operação dos núcleos;
6.  indícios de thermal throttling;
7.  relação entre o desempenho observado e as características do
    processador.

O experimento constitui uma linha de base para comparações futuras com
outros processadores e aceleradores, incluindo o Intel Atom N2600, a GPU
integrada Intel Iris Plus e, posteriormente, uma GPU NVIDIA RTX 5090.

------------------------------------------------------------------------

# 3. Configuração do `llama.cpp`

O `llama.cpp` foi compilado em modo Release com otimizações nativas da
arquitetura:

``` bash
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_NATIVE=ON
cmake --build build --config Release -j8
```

O processador possui suporte a extensões SIMD relevantes para
inferência:

-   SSE4.2
-   AVX
-   AVX2
-   FMA

Essas extensões representam uma diferença arquitetural importante em
relação ao Intel Atom N2600 utilizado em outro experimento, que não
possui AVX/AVX2/FMA.

------------------------------------------------------------------------

# 4. Benchmark de desempenho --- `llama-bench`

O benchmark principal foi executado com:

``` bash
./llama-bench \
  -m ../../../qwen2.5-0.5b-instruct-q5_k_m.gguf \
  -t 1,2,4,8 \
  -p 128 \
  -n 256 \
  -r 5
```

Foram realizadas cinco repetições para cada configuração.

## 4.1. Resultados

    Threads   Prompt processing (pp128)   Text generation (tg256)
  --------- --------------------------- -------------------------
          1            52,44 ± 0,62 t/s          26,88 ± 0,23 t/s
          2           100,82 ± 0,41 t/s          45,14 ± 2,06 t/s
          4       **128,95 ± 0,62 t/s**      **59,09 ± 0,04 t/s**
          8           125,72 ± 1,78 t/s          59,56 ± 0,61 t/s

### 4.2. Processamento de prompt

O desempenho de prompt aumentou significativamente entre 1 e 4 threads:

-   1 thread: 52,44 t/s
-   2 threads: 100,82 t/s
-   4 threads: 128,95 t/s
-   8 threads: 125,72 t/s

O melhor resultado foi obtido com **4 threads**, com 128,95 t/s.

A passagem de 4 para 8 threads produziu uma pequena redução:

``` text
128,95 → 125,72 t/s
```

Isso corresponde a aproximadamente **-2,5%**.

Portanto, para processamento de prompt, o uso de todos os 8 threads
lógicos não trouxe benefício.

### 4.3. Geração de tokens

A geração apresentou:

-   1 thread: 26,88 t/s
-   2 threads: 45,14 t/s
-   4 threads: 59,09 t/s
-   8 threads: 59,56 t/s

A configuração de 4 threads apresentou 59,09 t/s, enquanto 8 threads
apresentaram 59,56 t/s.

O ganho absoluto foi de apenas:

``` text
59,56 - 59,09 = 0,47 t/s
```

ou aproximadamente:

``` text
+0,8%
```

Esse resultado demonstra **saturação prática do ganho de paralelismo a
partir de 4 threads** para o modelo e protocolo testados.

Assim, embora o processador possua 8 threads lógicos, a utilização de 8
threads não proporcionou ganho significativo sobre os 4 núcleos físicos.

------------------------------------------------------------------------

# 5. Configuração considerada mais eficiente

Com base no `llama-bench`, a configuração de **4 threads** foi
considerada a principal linha de base do experimento.

Ela apresentou:

-   maior desempenho de prompt;
-   praticamente o mesmo desempenho de geração que 8 threads;
-   menor necessidade de threads lógicos;
-   melhor correspondência com a topologia física de 4 núcleos do
    processador.

A diferença de geração entre 4 e 8 threads foi suficientemente pequena
para ser considerada marginal neste experimento.

Portanto:

``` text
THREADS = 4
```

foi adotado como configuração padrão para o benchmark térmico.

------------------------------------------------------------------------

# 6. Teste interativo

Após o benchmark sintético, foi realizada uma execução interativa:

``` bash
./llama-cli \
  -m ../../../qwen2.5-0.5b-instruct-q5_k_m.gguf \
  -t 8 \
  -c 1024 \
  -n 256
```

O teste foi realizado com 8 threads para observar o comportamento real
da inferência no modo interativo.

## 6.1. Desempenho observado

Durante a geração, foram observadas taxas aproximadamente entre:

``` text
58–62 tokens/s
```

Esse intervalo é consistente com os resultados do `llama-bench`, que
registrou:

``` text
4 threads: 59,09 t/s
8 threads: 59,56 t/s
```

Portanto, o teste interativo confirmou a ordem de grandeza do benchmark
sintético.

O processamento de prompt apresentou valores variáveis dependendo do
tamanho do contexto, com medições observadas aproximadamente entre **8,5
e 170 t/s**.

Essa variação é esperada porque o custo de processamento do prompt
depende da quantidade de tokens processados e das condições específicas
da execução.

------------------------------------------------------------------------

# 7. Avaliação qualitativa das respostas

O teste interativo também revelou limitações importantes na qualidade
factual do modelo.

Foram observados exemplos de respostas incorretas ou inconsistentes,
incluindo:

### 7.1. Presidente do Brasil

O modelo afirmou que o presidente do Brasil era **Jair Bolsonaro**,
demonstrando informação factual desatualizada/incorreta para o contexto
do teste.

### 7.2. Datas relacionadas a Lula

O modelo apresentou confusão ao responder sobre os períodos relacionados
à presidência de Luiz Inácio Lula da Silva.

### 7.3. Localização de Camaquã

Quando questionado sobre Camaquã, o modelo apresentou respostas
contraditórias, associando o município a diferentes estados brasileiros,
incluindo:

-   São Paulo;
-   Ceará;
-   Rio de Janeiro.

### 7.4. Questão sobre "primeiro assunto"

Em uma pergunta sobre o primeiro assunto discutido, o modelo produziu
uma resposta associada ao Facebook, sem correspondência adequada com o
histórico da interação.

------------------------------------------------------------------------

# 8. Interpretação da qualidade do modelo

Os erros observados não indicam falha do `llama.cpp` ou do processador.

O motor executou a inferência normalmente e apresentou taxas de geração
compatíveis com o benchmark sintético.

Os problemas estão relacionados principalmente à capacidade e ao
conhecimento do modelo utilizado.

O modelo identificado pelo `llama-bench` possui aproximadamente **630
milhões de parâmetros**, sendo portanto uma configuração extremamente
pequena para tarefas que exigem conhecimento factual robusto e
raciocínio complexo.

Consequentemente, o teste demonstra duas propriedades distintas:

1.  **o hardware/software consegue realizar inferência local em alta
    velocidade para um modelo pequeno;**
2.  **a velocidade obtida não implica qualidade factual equivalente à de
    modelos maiores.**

Essa distinção é importante para os experimentos seguintes.

------------------------------------------------------------------------

# 9. Benchmark térmico

Foi executado um benchmark térmico específico para o Intel Core
i5-1035G1.

O monitoramento utilizou o subsistema `coretemp` do Linux e registrou:

-   temperatura do package;
-   temperatura de cada núcleo;
-   frequência de cada CPU lógica;
-   carga do sistema;
-   contador de thermal throttling.

O objetivo foi verificar se o desempenho observado estava limitado por
temperatura.

------------------------------------------------------------------------

# 11. Análise térmica

Os dados não indicam uma condição de superaquecimento durante o ensaio.

O processador atingiu temperaturas suficientemente elevadas para
caracterizar uma carga computacional relevante, mas permaneceu abaixo de
uma condição em que a temperatura, isoladamente, demonstrasse limitação
evidente do desempenho.

O resultado é particularmente relevante porque o benchmark de geração
manteve aproximadamente 59--60 tokens/s enquanto o package permaneceu
abaixo de 80 °C.

Portanto, **não há evidência, nos dados coletados, de que o desempenho
do `llama.cpp` tenha sido limitado termicamente durante o experimento.**

# 13. Thermal throttling

O contador registrado foi:

``` text
throttle_count = 3580
```

O valor mínimo, médio e máximo permaneceram iguais:

``` text
3580
```

Isso significa que, dentro da série temporal apresentada, o contador não
variou.

Portanto, **não é correto interpretar o valor 3580 como 3580 eventos
ocorridos durante este benchmark**.

Para determinar definitivamente se houve thermal throttling durante o
ensaio, o procedimento correto é comparar o contador antes e depois:

``` text
throttling durante o experimento =
contador_final - contador_inicial
```

Se ambos forem 3580, então:

``` text
0 eventos adicionais
```

No conjunto de dados atualmente disponível, o resultado é consistente
com a ausência de incremento do contador durante a janela monitorada.

# 15. Conclusões

O experimento demonstrou que o Intel Core i5-1035G1 é capaz de executar
localmente um modelo de linguagem quantizado pequeno com desempenho
superior a **59 tokens/s** em geração.

O resultado mais importante do benchmark de paralelismo foi a
identificação de um ponto de saturação próximo aos quatro núcleos
físicos. A utilização de oito threads lógicos produziu apenas
aproximadamente **0,8% de ganho** na geração em relação a quatro threads
e reduziu ligeiramente o desempenho de processamento de prompt.

Esse comportamento indica que, para o modelo e implementação avaliados,
o Hyper-Threading possui contribuição marginal para o throughput de
geração.

O benchmark térmico mostrou comportamento estável. A temperatura máxima
do package foi de **79 °C**, enquanto as temperaturas médias dos núcleos
permaneceram entre **58,7 °C e 68 °C**. Não foi observado aumento do
contador de throttling na série apresentada.

A execução interativa confirmou a ordem de grandeza do `llama-bench`,
apresentando aproximadamente **58--62 tokens/s** durante a geração.

Entretanto, o teste também mostrou que o desempenho computacional não
deve ser confundido com qualidade de resposta. O modelo apresentou erros
factuais significativos, especialmente em perguntas sobre geografia
brasileira, política e histórico da conversa. Isso reforça a necessidade
de avaliar separadamente **desempenho de inferência** e **qualidade do
modelo**.

------------------------------------------------------------------------

# 16. Limitações do experimento

Os resultados devem ser interpretados considerando as seguintes
limitações:

1.  O modelo utilizado é pequeno, portanto os resultados não representam
    diretamente o desempenho do i5-1035G1 com modelos maiores.
2.  O nome do arquivo não corresponde exatamente à identificação
    retornada pelo `llama-bench`; o benchmark identificou
    aproximadamente 630 milhões de parâmetros.
3.  O teste de qualidade factual foi exploratório e não constitui uma
    avaliação quantitativa de qualidade de LLM.
4.  O contador de throttling apresentado precisa ser comparado
    explicitamente entre início e fim para quantificar eventos ocorridos
    durante o teste.
5.  O experimento não mediu diretamente potência elétrica nem energia
    consumida.
6.  O resultado térmico depende das condições ambientais, do estado
    térmico inicial e do sistema de refrigeração do notebook.
7.  A execução interativa foi feita com 8 threads, enquanto o benchmark
    térmico foi projetado em torno da configuração de 4 threads,
    portanto esses ensaios não são completamente equivalentes.

# 17. Próximos experimentos

Para transformar esta linha de base em uma caracterização mais completa,
recomenda-se:

## 17.1. Modelos maiores

Executar o mesmo protocolo com diferentes escalas:

``` text
~0,5–1 B
~3 B
~7–8 B
```

utilizando quantizações comparáveis, especialmente Q4 e Q5.

Isso permitirá observar como o throughput muda com o tamanho do modelo.

## 17.2. Comparação de threads

Repetir sistematicamente:

``` text
1 → 2 → 4 → 8 threads
```

para cada modelo.

## 17.3. Medição de energia

Adicionar leitura de RAPL/powercap para obter:

-   potência do package;
-   energia consumida;
-   energia por inferência;
-   tokens por joule.

Uma métrica particularmente interessante será:

``` text
tokens/J
```

permitindo comparar desempenho e eficiência energética.

## 17.4. Teste da Intel Iris Plus

Depois da linha de base CPU, executar o mesmo modelo utilizando o
backend Vulkan da `llama.cpp`, quando suportado pela configuração do
sistema.

A comparação será:

``` text
CPU AVX2/FMA
        vs.
Intel Iris Plus G1 / Vulkan
```

## 17.5. Comparação com o Atom N2600

Executar protocolo equivalente no AOD270 com o Intel Atom N2600.

Essa comparação é especialmente interessante porque os processadores
possuem características SIMD muito diferentes:

``` text
Atom N2600
- SSE/SSSE3
- sem AVX
- sem AVX2
- sem FMA

Core i5-1035G1
- SSE4.2
- AVX
- AVX2
- FMA
```

Isso permitirá medir experimentalmente o impacto dessas extensões sobre
inferência local de LLM.
